Technical Audit & Inventory Module: PrismPDF Android AOSP

PrismPDF Core Architecture Report

Comprehensive system audit of active codebase files, OpenCV computer vision pipelines, coordinate mapping viewports, and identification of text-parsing functional shortcomings.

Architectural Finding: Static "Sticker Injector" vs. Semantic PDF Editing

The current implementation of PrismPDFEditorScreen and DocumentSessionViewModel executes touch taps by mapping coordinates, running background OpenCV inpainting to erase local pixel regions, and overlaying a hardcoded string or a static stub (e.g. "Salary Breakups" or "New Text"). It lacks a true PDF character extraction or Optical Character Recognition (OCR) parser bound to text vector streams, causing it to operate as a visual patcher rather than an intelligent semantic document modifier.

Code Analysis & Functional Shortcomings

1. Tap Handling Pipeline & Pixel Vector Processing

Shortcoming

In PrismPDFEditorScreen.kt, screen taps are captured via detectTapGestures in CORNER_TEXT_INJECTOR mode. The touch offset is converted via mapper.screenToPdf() and passed to SubPixelSnappingEngine using an OpenCV edge tracking binary mask. However, this only snaps to geometric edges (lines/borders), not text boundaries.

// Current behavior in PrismPDFEditorScreen.kt:
val extractedDocText = try { "Salary Breakups" } catch (e: Exception) { "" }
// Issue: Hardcoded stub string instead of inspecting underlying PDF text streams or OCR bboxes.

2. Absence of True Text-Parsing / OCR Extraction Hooks

Missing Module

The repository contains robust CV pipelines for image inpainting (BackgroundTextureSynthesizer) and edge detection (MultiChannelEdgeTracker), but lacks a character recognition (OCR) or PDF text-stream parser (such as Apache PDFBox text stripper or ML Kit Text Recognition). Consequently, when a user taps a line of text, the system cannot query what word is printed at those PDF coordinates.

3. Why Static Layout Elements Are Generated

Root Cause

Because the application renders documents into high-DPI immutable bitmaps via `PdfRenderer`, the underlying text semantics of the PDF are rasterized into pixels. Without an active bounding-box text-lookup engine or OCR indexing pass during workspace initialization, the editor treats the document purely as an image canvas. Tapping erases a rectangular pixel patch and places an empty or stub text overlay on top, resulting in static "sticker injection" behavior.

03

The Recovery & Implementation Baseline

To transition from a static raster patcher to a true semantic PDF editor, the architecture must integrate a text bounding-box extraction pipeline. Here is the exact roadmap and decoupled structure required:

1

PDF Text Stream Indexing Engine

Integrate Android PDFBox or native `PdfRenderer` text-character bounding box querying during `loadDocumentWorkspace()` to build an in-memory spatial index of text strings and their exact PDF point coordinates.

2

Spatial Hit-Testing Lookup

Replace stub strings (`"Salary Breakups"`) in `PrismPDFEditorScreen` with a spatial lookup query: `spatialIndex.findTextAt(clickPdfPoint)` to retrieve the exact word/sentence underneath the touch pointer.

3

Font Metrics & Typeface Matching

Extract source font size, weight, and typeface metrics from the PDF stream so replacement overlays match surrounding document typography flawlessly.
